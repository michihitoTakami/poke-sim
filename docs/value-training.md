# 勝敗価値の事前学習とV_refの学習

PR #15で生成したデータから公開状態の勝敗予測を事前学習し、固定参照方策の終局勝敗で調整する。
学習・開発評価・モデル保存までを扱う。探索への接続と実戦での採用は後続の工程。

## 入力と特徴量

`data/processed/public_value/`の次の生成物を使用する。

- `showdown-replays-v2/{train,development}.jsonl.gz`とそのmanifest
- `reference-{train,development}-v1.jsonl`とそれぞれのmanifest

元データの作り方は[公開観測の価値データ生成](public-value-data.md)を参照。
不明勝敗、初手を強制した判断、未来の勝敗が観測に混入した行、参照方策の異なる行は学習へ入れない。
元対戦のIDを正規化し、公開リプレイ・分岐対戦の学習用・開発用の4集合に重複がないことを検証する。
calibration/testは読み込まない。既存のsplitを再作成しない。

特徴量`observed-value-v1`はJSON観測だけを入力とする。

- 公開側588次元: 公開されたHP・状態異常・能力変化・技の効果、種族の基礎能力・タイプ、公開済み持ち物・特性、
  身代わり等の状態、見せ合い、場の状態、ターン数。場・控え・プレビューを区別する。
- 本人の非公開側277次元: 選出した控え、自分の正確なHP・能力値・持ち物・特性・技、場の技のPP・使用不能状態。
- 欠損mask: 未公開とHPゼロ・PPゼロ・持ち物消失を区別する。公開リプレイの非公開側は全て欠損にする。
- 控え・プレビューは集合として集計し、並び順に依存しない。種族名は図鑑の静的能力・タイプへ変換する。
- 対戦ID、勝敗、出所、レート、rootの候補手、乱数seed、実際に選んだ手はモデル入力にしない。

正確な毒の進行カウンタ・控えの残PP・未公開の相手セットなど、観測にない情報は復元しない。
公開ログ中の履歴を系列モデルで処理する実装も、この初版には含めない。

## 特徴量を準備する

ビルド済みの固定Showdownから、この実験用の図鑑を出力する。エンジン更新は不要。
以下は初回の実行例。既存の特徴量・実行ディレクトリは上書きしないため、別実験には新しい名前を使う。

```bash
node services/dex-export/export.js "$PWD/external/pokemon-showdown" \
  gen9championsbssregmc data/processed/public_value/training-dex-v1.json

uv run python -m pokesim.value.dataset \
  --base data/processed/public_value \
  --dex data/processed/public_value/training-dex-v1.json \
  --out data/processed/public_value/features-v1
```

4つの圧縮NPZ、図鑑のコピー、特徴量の名前・コード・入力・出力SHAを含むmanifestを保存する。
モデルは勝敗の0/0.5/1を割引なしで学習し、HPや対戦の短さを教師に加点しない。
元データの試行内の重みを保持したうえで、**元対戦ごとの合計重みを1**へ正規化する。
長い対戦、分岐数・world数の多い対戦が自動的に重くならない。

## 事前学習とV_refを比較する

```bash
uv run python -m pokesim.value.train \
  --data data/processed/public_value/features-v1 \
  --out runs/terminal-value-v1 \
  --device cuda --seeds 0 1 2
```

CUDAがない環境では`--device cpu`を指定する。追加の学習ライブラリは不要。
既定は公開側最大30epoch、V_ref最大50epoch、patience 8、batch 1024。
公開側の学習率は0.001、V_refは0.0003、AdamWのweight decayは0.001。
96→48の小さな公開側MLPと、本人の非公開情報を加える残差MLPを使う。

各seedについて以下を実行する。

1. 公開リプレイで公開側だけを学習する。
2. 同じ初期値からV_refを学習する（`scratch`）。
3. 事前学習した公開側を引き継ぎ、公開側も更新しながらV_refを学習する（`pretrained`）。

初期の非公開側残差はゼロ。同じseedの調整学習には同じミニバッチ順を使う。
開発用log lossでepochを選択し、全seedの確率を等重みで平均する。最も良かったseedだけを選ばない。
事前学習だけの予測をV_refへ直接転用した`transfer`も比較する。
基準はtrainの一定勝率と、公開HP・生存数・公開数・ターンだけの正則化ロジスティック回帰。
人間の勝敗と参照方策の勝敗を一つの教師として混ぜない。

## 出力を確認する

```bash
uv run python -m pokesim.value.evaluate --run runs/terminal-value-v1
```

このコマンドは保存済みの開発評価結果を表示する。評価計算自体は学習コマンドの最後に実行する。

- `public/scratch/pretrained-seed{0,1,2}.pt`: 選択した重み9個。特徴量名、データID、図鑑SHA、参照方策の版、
  相手プール、設定、コードSHA、PyTorch・実行環境、選択epochを保持する。
- `manifest.json`: 実行条件。データや特徴量コードの不一致を検出する。
- `report.json`: 各seed・平均予測のBrier、log loss、較正bin、元対戦単位のbootstrap区間、学習履歴。
- `{public,reference}-development-predictions.npz`: 元対戦ID・教師・重み・各方式の予測。教師はモデル入力に含めない。

全体に加え、序盤・中盤・終盤、毒/あくび、積み、回復技保有、バトン技保有、身代わり中の各集合を集計する。
「回復技保有」「バトン技保有」は利用可能な技情報による集合であり、その手の選択の良し悪しを測る指標ではない。
区間は元対戦を2,000回再標本化し、方式の差も同じ対戦を対応させて計算する。
これらはepoch選択にも使った開発集合での条件付き比較であり、最終的な未見testの結果ではない。

## 初回実行の結果（2026-10-16）

実行コード`65df432adb5f`、固定エンジン`942cda71`、PyTorch `2.11.0+cu128`、RTX 5060 Ti。
公開リプレイは学習4,218戦/開発740戦、分岐対戦は元対戦で学習34戦/開発19戦。
保存済みモデルを読み直し、平均予測と評価指標が保存結果に一致することを確認した。

| 開発データ | 方式 | Brier ↓ | log loss ↓ |
| --- | --- | ---: | ---: |
| 公開リプレイ740戦 | 一定勝率 | 0.25000 | 0.69315 |
| 同上 | HP等の基準 | 0.20604 | 0.59624 |
| 同上 | 公開側の事前学習 | **0.18765** | **0.54908** |
| 分岐対戦19戦 | 一定勝率 | 0.25256 | 0.69858 |
| 同上 | HP等の基準 | 0.15368 | 0.46567 |
| 同上 | 事前学習なしV_ref | 0.14821 | 0.46894 |
| 同上 | 事前学習のみを転用 | 0.15273 | 0.46365 |
| 同上 | 事前学習ありV_ref | **0.13218** | **0.41500** |

V_refの事前学習あり−なしの差は、Brier −0.01603（95%区間 −0.03021〜−0.00219）、
log loss −0.05393（−0.10266〜−0.00901）。各seedでも事前学習ありが改善した。
HP基準との差はBrier −0.02150（−0.04043〜−0.00182）、
log loss −0.05067（−0.10524〜+0.01039）。log lossでは改善を断定できない。
毒/あくびのV_ref開発集合は元対戦3戦のみで、その集計だけから改善を確定しない。

集約した数値とハッシュは[初回学習の結果JSON](audits/20261016-value-training.json)に保存した。
モデル・全評価・検証記録はサーバ上の`runs/terminal-value-v1/`、特徴量は`data/processed/public_value/features-v1/`にある。
大容量の入力と重みはリポジトリへ追加しない。

公開リプレイの利用は有効そうであり、次の候補は事前学習ありV_ref。
**次は別の元対戦・別seedで手の順位と終局勝率を比較する。** この段階では、探索への接続も実戦の勝率改善も確認していない。
