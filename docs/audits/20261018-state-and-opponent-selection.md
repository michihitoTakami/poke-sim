# 2026-10-18 探索盤面の修復と相手の選出予測

04:20:24までの213戦は93勝120敗（43.7%）。今回の優先順位は、観測した事実を正しく探索へ渡すことと、
相手がこちらの6体を見て選ぶ3体を推測すること。誤った盤面を入力したままの追加学習では改善の根拠が弱い。
比較元は`c87e995`。原本ハッシュと旧新の実装ハッシュは[修正前](20261018-state-before.json)・
[修正後](20261018-state-after.json)に保存した。

## 探索へ渡す盤面

選出記録が整合する209戦・2,175通常判断を、そのターンまでの公開ログだけで再構成した。
4戦の保存選出不一致は除外理由付きで記録した。相手の型は公開事前分布から1仮説ずつ生成し、
対象対戦や後の実戦記録を型の事前分布に入れていない。

| 確認項目 | 不一致の判断数・修正前 | 修正後 |
|---|---:|---:|
| 自軍の現在の持ち物 | 1,366 | 0 |
| 累計ひんし数 | 1,456 | 0 |
| 公開済みのメガ形態 | 103 | 0 |
| イリュージョン解除後の既知の相手技 | 4 | 0 |
| いずれかの不一致（重複を統合） | 1,690 | 0 |

これは上記項目の照合であり、全メカニクスを完全に復元できるという意味ではない。

- 元の構築の持ち物が探索で復活していた。消費・除去・交換後の持ち物を両陣営とも復元し、
  未知と空欄を区別する。手入力・リプレイ用の`BattleSession`も消費品をリクエスト更新で復活させない。
  ふうせん消費後のじしん無効や、オボンのみの再発動を防ぐ。
- ひんしフラグだけを戻し、`totalFainted`を戻していなかった。
  公開された累計を保持し、おはかまいり・そうだいしょうへ反映する。蘇生後も累計は減らさない。
- メガ済みでも、仮説の持ち物によって通常形態へ戻る場合があった。
  公開された形態と石を保持し、X/Y/Zの違いも固定する。
  `|-mega|識別子|元の種族|石`とpoke-envの読み方の違いも吸収する。
  通常メガが存在するルカリオでもZの種族値を上書きしない。
- イリュージョン解除時、偽装先の空のHPを倒れた控えとして扱い、既知の技も引き継いでいなかった。
  今の登場で公開された技・持ち物・能力変化を正体へ渡す。偽装先が以前本当に登場した場合は、
  その本来の履歴を復元する。誤った種族で作ったダメージ・素早さの推論資料は隔離する。

独立して動かしたシミュレータと、味方2体の実際のひんし後のおはかまいり・そうだいしょうのダメージを照合した。
持ち物の消費、交換、メガX/Y/Z、イリュージョン前後、推論資料の隔離にも回帰試験を追加した。

[6実戦局面の再評価](20261018-state-replays.json)は同じ既存NN、4.5秒・2ワーカーで実施した。
型の事前分布には自分の実戦記録を混ぜず、入力は観測済みの範囲に限定した。
2局面で判断が変わったが、変更手を同じ仮説で終局まで比較した結果は両方とも同じだった。
おはかまいり局面は16/24対16/24、相手フラエッテの局面は0/24対0/24。
これを勝率向上の証拠として扱わない。今回保証を増やしたのは盤面の整合性である。

## 相手の3体をどう読むか

旧`PickModel.predict(species)`は相手6種の一般的な選出率・先発率を返すだけで、こちらの6体を入力しない。
さらに探索の未登場の相手は、見せ合いから一様に並べ替えて補っていた。
選出画面に表示した予測と、実際の探索の仮説が一致していなかった。

`predict(species, roster=..., records=...)`に、こちらと同じ見せ合い6体に対する完了済みレート戦からの補正を追加した。
先発と控え2体の60候補を同時に扱い、選ばれる種族・先発・同時選出の組を正則化して学習する。
一般の選出率が事前分布で、少数の履歴で確率を0や1にしない。新しい自軍6体で履歴がないときは事前分布へ戻る。
勝敗やこちらが実際に選んだ3体は相手選出モデルの入力に使わない。

相手が2体しか見せずに終わった試合では、残り4種を不選出と決め付けない。
観測と整合する複数の3体候補を教師として扱う。未解除のイリュージョンは種族の曖昧さも残す。
局所的な予測であり、対戦相手のあらゆる心理や未経験構築への対策を学べたとは扱わない。

接続先は以下の通り。

1. ラダーと対戦サポートAPIの自軍選出評価。予想3体の組み合わせごとの弱点と、予測外の選出への30%の備えを使う。
2. 対戦中の未登場の控え。出場済みの相手全てを含む3体候補に条件付けてサンプルする。
   選出時点の予測をその対戦に固定し、別対戦の予測を流用しない。
3. 操作画面に予想3体を表示し、対戦記録に候補・確率・学習資料の識別子を残す。

208戦が相手選出学習の条件に合致した。直近60戦を古い順に、各対戦より前の履歴だけで予測した
[前向き比較](20261018-opponent-selection.json)は次の通り。

| 指標 | 旧一般率 | 自軍6体に対する補正 |
|---|---:|---:|
| 観測された先発・出場と整合する候補の対数損失（60戦、小さいほど良い） | 3.8010 | 3.3778 |
| 正体が確定した先発の的中率（58戦） | 18.97% | 29.31% |
| 3体が判明した選出のBrier（47戦、小さいほど良い） | 0.25683 | 0.22725 |

同じ履歴・同じ型仮説による[直近40件の自軍選出比較](20261018-opponent-choice.json)では、
決定的に最上位を選ぶと40件とも自軍の推奨3体は同じだった。
相手の予測が改善したことと、自分の選出が改善したことを混同しない。
既存の履歴評価・静的相性には依然として限界があり、交代・積み・バトンを含む完全な選出探索ではない。
対戦中の相手控えの生成は変更される。

## 運用と再実行

盤面の版は`observed-state-v2`として記録し、旧版の勝率較正を再利用しない。
データ作成コードのハッシュに形態処理も含め、古い観測成果物との混在を検出する。
既存のNNを使い、今回の比較対象に合わせた重み更新は行っていない。

ラダー収集は対戦終了後のコード更新検知で再読込する。対戦サポートAPIへの反映には再起動が必要。
ローカル対戦の[接続確認](20261018-state-local.json)は2戦2勝、両方とも探索失敗・fallbackは0。
少数のボット戦であり、実戦勝率の改善は未確認である。
本体の作業ツリーで全460テスト、ruff、Node/画面JavaScriptの構文確認、差分の空白チェックを通過した。

```bash
uv run python scripts/audit_state_integrity.py --until 20261018-042024 --out /tmp/state-audit.json
uv run python scripts/eval_opponent_selection.py --until 20261018-042024 --out /tmp/opponent-predictions.json
uv run python scripts/eval_opponent_selection.py --until 20261018-042024 --last 40 --choices --out /tmp/own-choices.json
uv run python scripts/eval_state_integrity.py --cases docs/audits/20261018-state-cases.json --out /tmp/state-replay
uv run pytest -q
```

旧版を再評価するときは同じスクリプトに`PYTHONPATH=<c87e995のsource>/src`を指定し、
旧版と新版それぞれのデータ・エンジンへのパスを揃える。
`eval_state_integrity.py --compare <旧report.json>`で新版の仮説内の終局比較も保存できる。
時間制限付き探索の試行数と同程度の候補手は、実行環境の負荷によって変わることがある。
