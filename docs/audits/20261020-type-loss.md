# でんこうそうげき・もえつきる後のタイプ消失の復元

PR45の19戦目、`20261020-050357-2701224222.json`で探索が失敗し、
05:03:58 JSTに収集が品質停止した。原因はパーモットのDouble Shock後の
`|-start|p2a: Pawmot|typechange|???/Fighting`だった。
6・7・10（強制交代）・11・12ターンの5判断がランダム手へ落ちた。

## 原因と変更

Showdown本体の技処理は、Double Shockでは電気、Burn Upでは炎のスロットを`???`へ置換する。
これは非公開・未判明のタイプではなく、失われたタイプのスロットである。
単タイプなら`???`、複合タイプなら例えば`???/Fighting`、`???/Flying`になる。
ノーマルへの置換や`???`の削除は、ゴーストの相性やBurn Up＋Roostの接地判定を変えてしまう。

PR45の状態境界には2つの取りこぼしがあった。

1. poke-envの`THREE_QUESTION_MARKS`を通常タイプと同じようにtitle-case化し、
   エンジン表記とは異なる`Three_Question_Marks`にしていた。
2. Node側は通常のタイプ表に存在するものだけを受け付け、正しい`???`も拒否していた。

`observed-state-v5`は、このenumだけを`???`へ変換し、Nodeでそのリテラルを明示的に許可する。
通常のタイプ・配列・アクティブ位置の検証は保持し、Stellar、空配列、不正文字列、nullは引き続き拒否する。
実際の相性・一致補正・技の再使用・交代時の解除は、現在のエンジンへ委ねる。
構築、NN重み、型事前分布、15秒予算、4ワーカー、品質停止条件は変更しない。

## 検証

- パーモットと単電気の個体のDouble Shock、単炎と炎・飛行の個体のBurn Upを、両陣営で検査。
  独立に開始した実際の対戦で技を使い、その公開ログをpoke-envへ読み込んでから再構築する。
  復元後のタイプ、攻撃ダメージ、地面とゴーストからの被ダメージが元の対戦と一致する。
  同じ技の再使用が失敗し、通常交代後には元のタイプへ戻ることも確認した。
- Burn Up後のRoost中に地面技が当たることを、同じ乱数系列の元対戦と復元対戦で比較した。
  被弾時のタイプが`???`のままで接地していることも確認し、ノーマルへの置換を検出する。
- 公開観測におけるタイプ表記の保持と、継続方策の一致補正消失・残ったタイプの地面相性も検査。
  不正なタイプの拒否と、既存のみずびたし対策のテストも通す。
- 停止した5判断すべてを、保存した本人の正確なrequestと、その判断時点までの公開ログで再実行した。
  4ワーカー・15秒予算・既存NNと相手モデルを使用し、全件で合法な判断を返した。
  フォールバック・シミュレーション失敗は0。判断時間は約8.9〜14.5秒。
  失敗局面を再利用した回帰確認であり、勝率が改善したという評価ではない。

Burn Up等の合成fixtureはエンジン境界の検査用で、現行レギュレーションの習得可能な型を生成するものではない。
原記録・再実行のhashと結果は[監査JSON](20261020-type-loss.json)に保存する。
全609テスト、変更PythonのRuff、Node構文、diff検査が成功。

更新は停止済みの収集を維持した状態でマージを反映し、ローカルShowdownと収集を再起動する。
元の対戦記録とcheckpointのhashを照合して、既存データの保持を確認する。
