# 実対戦のバトン状態・要求処理・素早さ候補の修正

[再起動後7戦の監査](20261016-post-restart.md)で確認した不具合に対応する。
サーフゴーへのアンコール失敗は「おうごんのからだ」による正常な挙動。
その対戦にあった5ターンの選択記録と実行技の不一致は、アンコールによる変更とは区別する。

## 実装

### バトン後の状態を実対戦から次の探索へ保持

- オンラインのAdvisorPlayerと、録画再構築・beliefのBattleSessionに同じTrackedBattleを使用する。
- 成功したバトン交代の直前に退出側の正負すべての能力ランクと引き継ぎ可能な効果を取得し、
  poke-envの通常交代処理後に受け手へ復元する。効果のコピー可否は実運用のShowdown形式の
  `noCopy` を参照し、アンコール・かなしばり等を引き継がない。
- 失敗・行動不能・瀕死・強制交代・次ターンへの持ち越しでは引き継がない。
- 技ロックのプロトコル追跡もオンラインと再構築で共有する。
- 再構築時の要求がチームファイルの元のdetailsで観測済みのメガの姿を上書きしないよう修正。

実ログ3件をテスト用prefixとして固定した。未来の対戦結果や相手の型をテスト入力に補完していない。
オンラインのメッセージ受信→次の要求、録画の再構築→次の要求→実エンジンの探索盤面の両方で、
素早さ+3、防御+6・素早さ+4・みがわり、特攻・特防+1を検証する。

### 終了済み・古い要求を破棄し、送信した選択を追跡

- 終了・待機中の要求を探索前に除外。探索中に終了・要求更新・待機へ変わった場合も、
  結果や例外を破棄し、品質停止の原因にしない。
- 終了後のメッセージで保存済みの対戦ログ・adviceを再生成しない。
- 各 `/choose` / `/team` コマンドに計算対象のrqidを付け、別の要求に適用されることを防ぐ。
  処理済み要求の重複送信と、古い要求による盤面の巻き戻しを防ぐ。
- 「選ぶものがない」「選択が遅すぎる」は古い選択への応答として記録し、再探索しない。
  それ以外の実際に拒否された現行要求にはサーバーの合法デフォルトを1回だけ送り、
  通常の価値探索運用では品質停止の対象とする。
- ラベルから注文への変換をstrictにし、変換内で黙ってランダム技に置き換えない。
- adviceにrqid・判断時の自分の状態・変換後の注文・送信完了したコマンドを保存する。
  送信試行・送信完了、終了後の要求、重複・古い要求、品質停止の詳細は
  出力先の `diagnostics.jsonl` に追記する。対戦レコードの終了処理後も記録が残る。
- 対戦パケットは1行ずつログへ反映し、要求を処理する時点より後の行を探索に見せない。

元の5件の不一致は送信コマンド・rqidの記録がないため、発生原因の確定には至っていない。
今回の修正は古い要求への誤適用を防ぎ、変換・送信・実行を次回から追跡可能にするもの。
元の不一致をアンコールのせいにしたり、原因特定済みと扱ったりはしない。

### 行動順と両立する相手の型を補充

- 48個の事前候補すべてが行動順の観測と矛盾した場合、合法な素早さ0〜32ポイント、
  性格、未判明時のみアイテムの候補を生成し、実エンジンで観測との整合性を確認する。
- 狭い素早さ区間にも対応するため、最大・最小だけでなく各ポイントを調べる。
  判明済みの技・特性・アイテムは保持し、各能力32・合計66ポイント以内にする。
  メガ進化済み個体には新しくスカーフを提案しない。
- 両立する候補がある場合、矛盾する素早さ候補には確率を割り当てない。
  ダメージの尤度下限は維持する。優先度・強制後攻等で素早さを推定できない観測は従来どおり除外する。
- 候補・尤度をキャッシュし、探索の各サンプルで同じ補充を繰り返さない。
- 候補数・整合する候補数・追加数・解消できない矛盾をadviceの `belief.speed_support` に記録する。
  どの提案でも説明できない観測を「正しい推定が得られた」とは扱わない。
- 素の事前候補APIと、過去の観測時点を指定する重み計算は維持する。

## 実局面での再計算

[3局面の結果JSON](20261016-live-state-fixes.json)に、判断時点までのprefixを用いた
オフライン照会を保存した。現在の事前分布を使用しており、元の実行との完全な条件統一比較ではない。

| 対戦・ターン | 変更前の実行記録 | 修正後の照会 |
| --- | --- | --- |
| `135307` T10 | HP1のペンドラーへ交代 | はねやすめ。防御+6・素早さ+4・みがわりを保持、素早さ426 |
| `135816` T16 | じこさいせい | 引き続きじこさいせい。自分136に対し相手候補101〜128へ修正 |
| `135816` T18 | じこさいせい（4回連続の開始） | シャドーボール。自分136に対し相手候補123〜129 |

3照会とも約7.89〜8.04秒、fallback・シミュレーション失敗なし。
T16の回復は残っており、「今回の修正で不要な回復がすべて解消した」とは判断しない。
相手には控えも残っているので、目の前の相手を倒せるだけで常に攻撃を強制する規則は追加していない。
盤面・素早さの誤認と、正しい入力での回復の戦略的評価を分けて検証する。

## 検証範囲

- 実ログ3件の引き継ぎと探索初期盤面、オンライン受信、正負のランク、コピー可否、
  通常交代・失敗・行動不能・瀕死・強制交代を回帰テスト化。
- 終了前後・探索中の要求更新、待機、古い要求、重複要求、要求ID付き送信、
  変換後の注文、現行要求の拒否、実際の対戦中のfallback停止と永続記録を検証。
- アンコールが実際に成功した場合のロックは既存テストで保持。
  おうごんのからだの `-immune` ではロックが作られず、4技が選べることを追加検証。
- 全候補が速すぎる事前分布からの候補補充、矛盾候補の確率0、キャッシュ再利用、
  未解決の矛盾の報告、アイテム・メガ・ポイント制約を追加検証。

ローカル対戦は輸送経路の検証に使用し、公式ラダーの強さの評価には使用しない。
まず1.5秒の短縮予算で1戦を実施し、20判断すべての選択技と実行技が一致、
ブラッキーからサーフゴーへ特攻・特防+2が次の判断まで保持された。
ただし探索期限切れが6判断あったため、この短縮試験を探索品質の合格結果とは扱わない。
通常の8.5秒設定でも1戦を実施し、14判断、最大8.02秒、fallback・シミュレーション失敗・
プロトコルエラー・選択と実行の不一致は0。防御+4・素早さ+3・みがわりが
ペンドラー→ブラッキー→サーフゴーへ引き継がれ、次の判断にも保持された。
両試験の各判断・送信内容・実行技は[結果JSON](20261016-live-state-fixes.json)に保存した。

最終ソースで `uv run python -m pytest -q` は全358件成功（58.90秒）。
変更したPythonファイルのRuffと `git diff --check` も成功。
