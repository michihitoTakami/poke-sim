# 相手ひんし直後のバトン交代で停止する問題

対象は `e46719646ad6` の公式ラダー記録
`data/raw/ladder/20261021-023430-2701738214.json`、13ターン目、要求ID 33。
原本SHA256は `dbbb276dfa79cb807102d2a353fd9a2611de1c58af4bd6ecb50ecfaecba61c0b`。

## 原因と修正

相手フシギバナがヘドロばくだん後にいのちのたま反動で倒れ、その後ブラッキーが
バトンタッチを実行した。こちらは生存中のブラッキーから交代先を選ぶ要求を受けたが、
Advisorは「相手ひんし・こちら生存」を探索対象から除外していた。
方策モデルを使わない本番設定では助言が空になり、ランダム交代が1回発生した。
試合には勝ったが、品質チェックにより対戦終了後に収集が停止した。

実際の交代要求なら相手がひんしでも探索する。サンプル世界にはこの途中段階を明示し、
Showdownへ「こちらの交代先を選ぶ→相手が次のポケモンを選ぶ→次の通常ターン」の
順で処理させる。バトンを通常交代として評価せず、能力上昇の引継ぎと設置技のダメージも
Showdown自身の交代処理で評価する。状態復元の版は `observed-state-v6`。

相手が生存している通常のバトンは、相手の未実行攻撃を表現する別の問題があるため、
今回の新しい途中段階の対象に含めない。同時ひんしの既存処理も維持する。
品質停止の条件は緩和しない。

## 検証

`tests/fixtures/baton-fainted-opponent.json` は、バトン実行までの公開履歴と、その時点の
自分の実際の要求だけを保存している。後の相手の交代先や技を探索入力にしない。
自分の配分は記録時点のH5/A31/S30を固定する。

本番と同じ既存の3モデル価値アンサンブル、相手方策、相手型集計を使って実局面を指し直した。
相手型集計SHA256は `68417072bb64f41f0cccb19ef3ca5bccf8fbd07801c7e5dcc3ed2f6075ef052b`。

これは不具合再現と修正確認であり、選択の最善性や勝率改善の証明ではない。

回帰テストは実際の要求から探索が呼ばれること、合法な交代候補、交代順序、
特攻・特防+4の引継ぎ、ステルスロック、探索snapshot往復を確認する。
とんぼがえりでは能力上昇をコピーしないことも確認する。
旧ボーマンダ配分に依存していた既存の速度・バトンテストは、当時の配分を明示して固定した。
全体テストは640件成功。変更したPythonのRuff、2つのJavaScriptの構文確認、
`git diff --check` も成功した。

モデルの再学習・重みの差し替えは行わない。いじっぱりH5/A31/S30、1判断15秒の設定を維持する。
