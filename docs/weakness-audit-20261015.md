# 戦術実装後の弱さの調査と修正順

調査対象: `02faed0e518a`。ラダー収集が継続中のため、集計は `20261015-230310-2698876202.json` までで固定した。これは既存記録を使った診断であり、改善版の前向きtestではない。今回の調査で読んだ40戦は、以後の候補の未見testとして扱わない。

## 結論

最優先は探索へ渡す自分側の選出・生存状態の修正。**未選出のポケモンが、探索の中で生きた味方として追加される不具合を再現した。** この状態で探索量や学習量を増やすと、誤った局面に対して強い手を探すことになる。

次に、終局まで評価した計画と、その直後に実行する1手を結びつける。現在の実装では計画の継続方策を選んだあと、追加5回の継続とHP採点を含む別の探索で実行手を決める。長い計画の改善が、そのまま実行手の改善になる構成ではない。

構築の変更を主対策にはしない。現行構築で手動の高順位実績があり、まず観測・復元・行動選択を信用できる状態にする。

## 2. P0: 選出していない味方が探索へ入る

該当箇所は [`Lookahead.own_side`](../src/pokesim/search/lookahead.py)。`available_switches` が空、拘束なし、強制交代先の指定なしのとき、`battle.team.values()` の先頭から控え2体を作り直す。

`battle.team`は見せ合い時の6体を保持し得る。一方、そのターンのrequestの`side.pokemon`は実際の選出メンバーを示す。この2つを同一視すると、最後の1体になった際に未選出の生きたメンバーが混ざる。

### 再現した実戦局面

対象: `data/raw/ladder/20261015-213706-2698835995.json`（原本はgit管理外）、12ターン目。

- 選出: サーフゴー、ペンドラー、フラエッテ。
- サーフゴーとフラエッテはすでに倒れ、実際の交代候補は0体。
- 保存ログを現行の`BattleSession`で復元すると、requestにはこの3体と正しい生存状態がある。
- `own_side`の出力は、ペンドラー、倒れたサーフゴー、**未選出のHP満タンのボーマンダ**になった。
- Node側の復元では生存2体となり、バトン先のボーマンダが存在する。

固定したギャラドスの仮説型・同じ乱数・同じ継続方策で比較した結果:

| 自分側の入力 | バトンの探索値（相手4候補の各列） |
|---|---|
| 現行の出力: 未選出ボーマンダあり | 全列 +0.990 |
| 実際の選出へ訂正: フラエッテはひんし | 全列 −0.975 |

これは相手の真の型を同定した反実仮想実験ではなく、**自分側の誤ったメンバーを直すだけで評価が反転する**ことを確かめた再現実験である。実戦ログでは、このターンと14〜17ターンに失敗するバトンを選び、評価は+0.98前後だった。

### 修正仕様

1. 通常対戦ではrequestの`side.pokemon`と保存した選出IDを、自分側メンバーの根拠にする。
2. 対戦メモリ内の6体を、交代候補が空だからという理由で補充しない。
3. ひんしメンバーも所属と生存状態を正しく保存する。拘束による「交代できない」と「控えがいない」を区別する。
4. メンバーID、生存数、HP、合法な交代先を、PythonのrequestとNode復元後で比較する。矛盾した局面を有効な探索として使わない。
5. 見せ合い6体→選出3体→2体ひんし、全メンバーの挿入順変更、拘束中、強制交代について回帰試験する。

この不具合を直しても、すでにペンドラーだけになった対戦を救えるとは限らない。攻撃役を失う前の判断も別途診断する。

## 3. P1: 計画の勝敗と、実際の1手の評価を合わせる

[`Advisor._search`](../src/pokesim/live/advisor.py)は、`_choose_plan`で選んだ名前を継続方策へ反映し、その後に通常のpayoff探索を行う。そのpayoffは追加5回の継続で打ち切り、未決着なら[`score`](../services/sim-tools/lookahead.js)のHP差・攻撃役有無の値を使う。

したがって「計画を終局まで対戦した」は「各候補手を終局勝敗で比較した」とは異なる。終局到達率の平均も46.5%で、未決着評価への依存が大きい。

次の比較を優先する。

1. 観測情報だけから8原則を使って実行手を選ぶ構築専用方策を、独立した比較候補にする。
2. rootの候補手それぞれを実行してから、同じ参照方策と相手プールで終局まで対戦し、手ごとの勝敗を比較する。
3. 計画の推奨初手、探索の初手、最終実行手を保存し、計画から離れた判断を可視化する。
4. 長期的にはV_refで打切りを評価する。HP差を勝敗教師へ変換しない。

計画のmaxTurns=60で未決着だった試行を、現在は勝敗差0として集計している。これは引分との混同を招く。未完了試行の割合と、全未完了を敗北/勝利と仮定した得点範囲を出し、順位が確定しない計画は追加評価または保留にする。失敗試行を除外したため有利になる候補も採用しない。

## 4. P2: 攻撃役を失う前の失敗を教師にする

最新40戦には、フラエッテがドドゲザンのアイアンヘッドやメガガメノデスのどくづきで毎回身代わりを壊され、再び身代わりを選ぶ例がある。21:37の対戦では対ドドゲザンで3・4ターン目に連続して身代わりを使用した。

ここで検証するのは「身代わり禁止」ではなく、次の点。

- 前ターンに観測した被ダメージ・技・身代わり破壊を次の判断へ反映しているか。
- 身代わりを作った手の攻撃開始までのHPと勝敗を、即攻撃・回復・交代と比較できるか。
- その攻撃役を失うと、残りの選出にどの勝ち筋が残るか。

20局面程度の小さな診断集合から開始し、ユーザーの推奨手・理由とbotの差を記録する。すでに詰んだ最後の数ターンだけを集めず、最初に勝ち筋を大きく失った判断へ遡る。修正で既知局面を改善したら、別の対戦・別の相手で確認する。

選出表の最新版記録にはpolicy hash等のmetadataがなく、どの操作者向けに作った表か不明。現在は警告後も選出に使用されている。構築を固定したまま、ユーザーの選出判断・現行操作者に対応する評価と照合する。

## 5. 順序と採用条件

1. **局面復元のP0を修正し、requestとの一致を回帰試験する。** その後、同じ40戦の主要局面を再評価する。改善勝率は新規対戦で測る。
2. **8原則の実行方策、現行探索、rootの終局比較を、同じ条件で比べる。** 深さやrhoの大量チューニングはこの後にする。
3. **攻撃役を失う前の局面を診断し、終局データとユーザーの判断で方策・価値を学習する。** 対応する選出表も検証する。
4. **型推定と行動抽選は独立因子として比較する。** 最新40戦では両方とも無効。マージ済みと運用有効化を区別する。

既存の`test_expert_continuation.py`、`test_state_codec.py`、`test_worker_transitions.py`は計35件合格した。今回の重大な不具合は、そのテストでは検出されていない。Python側の6体から3体への選別を含む境界試験を追加する必要がある。

固定した仮説型での比較結果を[局面復元の再現結果](audits/20261015-search-roster-reproduction.json)に保存した。原ログと一時作業ファイルはgit管理外であり、公開資料の再現に個人環境の`/tmp`は要求しない。自分側メンバーの選別とNodeへの引渡しは、[不具合修正PR #9](https://github.com/michihitoTakami/poke-sim/pull/9)の`tests/test_search_roster.py`で合成局面から再現する。

再現JSONの`worker_options`と各`samples`を使い、`samples: [sample]`を追加したリクエストを`node services/sim-tools/lookahead.js external/pokemon-showdown`へ1行のJSONで渡すと再計算できる。`expert`継続方策は戦術実装PRを取り込んだ版で利用する。

2026-10-16のPR準備時に、選出復元の修正単独で関連93件、戦術実装単独で関連53件、両者を取り込んだ状態で関連110件のテスト合格を確認した。勝率改善の検証は今後の新規対戦で行う。
